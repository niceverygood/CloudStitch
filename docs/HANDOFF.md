# Cloudstitch 프로젝트 인수인계

기준일: 2026-10-18. 이 문서는 다른 컴퓨터의 Codex에서 기존 작업을 그대로 이해하고 이어가기 위한 저장소 안내다. 경로는 모두 저장소 루트 기준이다.

2026-10-18 통합 이관: 사용자의 최신 요청은 현재 작업을 멈추고 Git push 및 데스크톱 인수인계를 마치는 것이다. 리깅·함대·별도6판 교전의 로컬 이력과 원격 `main`의 무기6종·VFX54파일·월드96자산/7장면을 함께 보존한다. 아래 제작 당시의 미커밋/미푸시 표현과441개/686개 집계는 각 과거 시점 기록이다. 현재 전체 파일 수·크기·해시는 `docs/asset-inventory.json`과 실제 Git/원격 상태를 기준으로 확인한다. ZIP·인증·원시 Meshy 응답·로컬 상태·의존성 캐시는 제외한다. 맥북 준비 안내 `outputs/handoff/MACBOOK_START.txt`도 보존한다.

이번 첫 전장의 최신 보충 인계는 [BATTLEFIELD_DESKTOP_HANDOFF-2026-10-18.md](BATTLEFIELD_DESKTOP_HANDOFF-2026-10-18.md), 데스크톱에 붙일 전문은 [BATTLEFIELD_DESKTOP_CONTINUE-2026-10-18.txt](BATTLEFIELD_DESKTOP_CONTINUE-2026-10-18.txt)다. 일반 `DESKTOP_*` 인계는 별도6판 교전 세션의 체크포인트로 함께 보존하며 두 시제품을 같은 구현으로 합치지 않는다.

## 1. 현재 프로젝트를 한 문장으로

**Cloudstitch · 클라우드스티치**는 구름 위 비행선을 조립·수리하고 적의 부품을 인양하며 기억의 주인을 찾아가는 싱글플레이어 액션 RPG 기획이다. 현재는 상세 기획·스토리보드·무드보드, 실제3D 모델, 리깅·함대·아트 작업대·시작화면과 플레이 가능한 첫 전장 `battlefield-v1`, 별도6판 교전 `encounters-v1`이 있다. 최종 게임 엔진·플랫폼과 전체 캠페인은 미정/후속이다. 첫 전장의 구현·검사는17절, 별도6판 교전은16절, 무기/VFX/월드 아트는18~20절을 따른다.

사용자가 최종 선택한 작품 이름은 `Cloudstitch`다. GitHub 저장소는 `https://github.com/niceverygood/CloudStitch`이며 대문자 S는 저장소 표기다. `구름을 꿰매는 배`는 의미를 설명하는 문구다. `검은 부력 / Black Buoyancy`, `홈와드 / Homeward`는 이전 이름이고, 과거 문서의 제목은 변경 이력 보존을 위해 그대로 남는다. 제목 기준 파일은 `outputs/game-title.json`이다.

## 2. 새 컴퓨터에서 준비

같은 Codex 계정으로 로그인해도 원래 PC의 폴더·PNG·GLB·npm 캐시는 자동으로 생기지 않는다. 저장소를 새 PC에 직접 내려받아야 한다.

```sh
git lfs install
git clone https://github.com/niceverygood/CloudStitch.git
cd CloudStitch
git lfs pull
git status
```

Git LFS는 별도 설치가 필요할 수 있다. PNG나 GLB가 LFS 포인터 텍스트 상태라면 실제 자산 다운로드를 완료한 뒤 뷰어를 테스트한다. 기존 체크아웃이 있다면 먼저 로컬 수정 상태를 확인하고 `git pull --ff-only`, `git lfs pull`로 갱신한다. 작업 중인 파일을 임의로 초기화하지 않는다.

Codex에서 clone한 폴더를 프로젝트로 연 다음 `AGENTS.md`와 이 문서를 읽고, `docs/CONTINUE_PROMPT.md`를 붙여넣는다. 기존 아트 뷰어 HTML 열람에는 별도 게임 엔진이나 빌드가 필요하지 않다. 첫 전장과 별도 교전 시제품은 저장소 루트의 로컬 HTTP 서버에서 열어 기존 함대 GLB를 상대 경로로 읽는다. 수정·재빌드·검사는 `tools/`의 의존성과 전용 README를 확인한다.

원래 PC의 Windows 절대 경로, Temp 클립보드 이미지, Codex 런타임/플러그인 캐시는 이식 가능한 의존성이 아니다. 필요한 기준 이미지는 `outputs/` 안에 저장되어 있다. API 키와 계정 인증은 저장소에 넣지 않는다.

## 4. 사용자의 의도와 시각 방향

사용자는 처음부터 비행선 중심의 게임 전반을 깊게 기획하고, 요소별로 많은 무드보드를 보며 방향을 고르기를 원했다. 전투, 시작화면, 스토리 모드, 항구·메뉴, 미션, 적·보스, 지도·지역, 성장·제작, 전리품·저주, 튜토리얼, UI·접근성, 엔딩까지 진행했다.

이후 기존의 어두운 기계 판타지에 **따뜻하고 감성적인 손그림의 분위기**를 더했다. 사용자는 완전한 사실적 3D보다는 WANDERBURG 성채 화면처럼 입체감이 있지만 그림으로 읽히는 표현을 선호했다. 최종 대화에서는 실제 3D로 만들면서도 2D 느낌을 낼 수 있는지 확인했고, 그에 맞춘 현재 비행선 뷰어를 만들었다. 참고 게임의 내부 엔진이나 구현 방식은 스크린샷만으로 확인한 것이 아니다.

선택 비행선의 시각 기준은 `outputs/selected-airship-toon3d/reference.png`다. 크림색 천 기낭, 따뜻한 목재, 청록색 엔진/프로펠러/지붕, 황동 테두리, 산호색 수선 천을 유지한다. 새로운 브랜드 시작화면은 수채화 아침 하늘, 구름 바다, 봉제한 천 글자와 이어지는 실을 사용한다. 로고·배경·비행선의 색과 재료가 한 작품으로 연결되어야 한다.

## 5. 기획·무드보드 아카이브

### 원본 기획

`outputs/FINAL-game-design-2026-10-17.html`에 기존 기획 전문과 생성·검토 기록을 통합했다. `outputs/` 루트에는 번호가 붙은 상세 TXT/JSON/PNG 원본이 있다. 마감 기록은 `outputs/FINAL-closeout.txt`, 전체 색인은 `outputs/FINAL-manifest.json`, 진행 기록은 `outputs/progress.json`에 남는다.

마감 집계 기준 상세 기획·검토 문서 **114개**, 전체 원본 PNG **122개**다. 장기 작업 중 새로 만든 보드 107장과 초기 참고·수정본을 포함한 전체 122장을 구분한다. 수정된 보드를 새 요소 완료 수로 중복 계산하지 않는다.

### 감성판

`outputs/emotional-edition/`은 원본 122장에 각각 대응하는 감성판 PNG 122장, 실제 생성 프롬프트, 진행/검사 기록을 보관한다. 통합본은 `FINAL-emotional-game-design.html`, 비교 페이지는 `moodboard-comparison.html`, 이미지 색인은 `image-manifest.json`, 완료 확인은 `verification.txt`다.

감성판은 원본 기획 전문을 지우거나 새 시스템으로 바꾼 자료가 아니다. 원본과 손그림 방향을 나란히 보존한다. 기존 문서에는 이전 제목이 남아 있을 수 있다. 새 브랜드가 확정되었다고 전체 기록을 무차별 치환하지 않는다.

### 기획의 핵심 축

- 전투: 기관총, 함포, 박격포, 작살포, 사슬탄, 화염방사기 6종. 갑판 회전대·측면 거치대·모듈 연결부의 장착을 구분한다. 무기의 포각·거리·장전·가림을 읽을 수 있어야 한다.
- 핵심 순환: 이동/조준 → 연결부 절단 → 적 부품을 묶음으로 분리 → 인양/회수 → 화물/제작/장착 → 손상 복구 → 귀환/정산 → 재출항.
- 모듈 구조: 핵심 선체를 루트로 하는 단일 부모 트리 초안. 부모 골조가 끊기면 하위 묶음이 분리된다. 함포만 파괴했다고 옆 엔진이 함께 떨어지지 않는다.
- 예산: 중량, 양력, 전력, 연료를 구별한다. 스크랩S·연료F·봉인 천C가 기획 자원이며 금화 화폐를 추가한 것으로 해석하지 않는다.
- 스킬: 기동·포격·인양 3계열 × 7노드 = 21노드 초안. 출항 레벨1~9, 총8포인트, 일반 액티브2개와 궁극1개. 확정된 최종 밸런스가 아니다.
- 이야기: 프롤로그·4개 주요 막·최종 항해와 3가지 대안 결말. ‘5막’ 표기는 최종 항해를 포함한 구조와 맞춰 읽는다.
- 기억 부품: 강한 장비 등급과 기억의 존재는 별개다. 성능 이점/대가와 반환·보관·봉인을 구별한다. 필수 단서에 무작위 드롭 잠금을 걸지 않는다.
- 복구: 정산 ID로 중복 보상 방지, 안전 경계 저장, 명시적 실패 안내. 정사 캠페인 저장은 아직 없으며 별도 교전 시제품은 판별 승리 표시만 저장한다.

## 7. 비행선 디자인 탐색과 3D 자산

### 초기 3D 9종

`outputs/airship-models-9/`에 A1~C3의 GLB와 미리보기가 있다. A는 포근한 수작업선, B는 거친 인양 작업선, C는 날렵한 바람 배달선이며 각 세 형태다. `index.html`, `designs.json`, `model-manifest.json`, `README.txt`를 함께 읽는다.

이 모델들은 약 **745,968~1,394,654개 삼각형**의 고밀도 디자인 탐색용 원본이다. 각각 단일 메시로 기록되어 있고, 생성 외형과 설계안의 차이도 문서화했다. 단일 메시라는 사실만으로 모든 정점이 물리적으로 이어져 있다고 단정할 수는 없다. 게임용 소켓·분리 부품·최적화·충돌·LOD가 완성된 자산이 아니다. 현재 선택 모델을 대신해 초기 9개 중 하나를 사용하기로 확정하지 않는다.

비용 이력: 초기9종 개별 작업 응답 합계270크레딧, 당시 계정 잔액 차이315크레딧, 차이45는 미확인으로 `billing-check.txt`에 기록되어 있다. 추가 청구나 중복 생성이 있었다고 추정해 확정하지 않는다.

### 입체감 있는 2D 9종

`outputs/2d-volume-airships/`에 A1~C3 PNG, `gameplay-style.png`, 갤러리, 생성 프롬프트, `pipeline-guide.txt`가 있다. 9종은 1536×1024 RGBA 투명 이미지이며 별도 게임 장면은1672×941 RGB다. 모두 정지 콘셉트이며 스프라이트 시트·방향별 프레임·부품 컷아웃·리그가 아니다.

| 생성 방식 | Meshy image-to-3D, smart-topology, 목표12,000삼각형 |

실제 소유 자산 원형은 이 GLB다. 원본 그림에 없는 후면·내부는 생성 도구가 추정했으므로 검토가 필요하다. 프로펠러·포탑·갈고리를 각각 움직이려면 부품 분리와 회전축 설정부터 해야 한다. 모델 전체에 캐릭터용 자동 리깅을 넣는 것이 첫 작업은 아니다. 단단한 기계 부품은 오브젝트 이동·회전으로 처리할 수 있고, 휘는 천이나 생물 구조에만 필요에 따라 뼈대/변형을 사용한다.

## 8. 손그림 3D 뷰어와 잔상 수정

우선 열 파일: `outputs/selected-airship-toon3d/viewer-v2.html`. 기존 `viewer.html`도 같은 수정본이다. GLB와 Three.js 번들을 HTML에 포함하여 CDN·외부서버 없이 로컬에서 열린다. 드래그 회전, 휠 확대, 이동, 초기 시점/화면 맞춤/자동 회전, 윤곽선 켜기와 두께 조절을 제공한다.

표시 모드:

- 손그림: 조명 반사를 배제한 베이스 컬러와 어두운 윤곽선.
- 셀 명암: `MeshToonMaterial`, 3단계 명암과 윤곽선.
- 원본 재질: 생성된 재질 표시.

정사영 카메라가 기본이며 재질 설정은 `toon-material-settings.json`에 있다. 이 효과는 뷰어 코드의 런타임 설정이다. GLB 파일 안에 엔진 공통의 셀 셰이더가 저장된 것은 아니다.

사용자는 회전 후 모델이 원형으로 겹쳐 쌓이는 화면을 신고했다. 원인은 `OutlineEffect`가 내부적으로 `renderer.autoClear`를 자신의 값으로 교체하지만 그 값이 초기화되어 있지 않아 이전 프레임을 지우지 않는 것이었다. 수정은 효과 인스턴스 생성 후 **`outlineEffect.autoClear = true`**를 명시하고 프레임당 중복 기본 렌더를 제거한 것이다. 모델은 재생성하지 않았으며 추가 생성 비용도 없다.

검증 기록: 실제 GLB에서 세 표시 모드 각각120프레임 자동 회전 후 멈춘 화면과 같은 카메라 각도를 깨끗하게 다시 그린 화면을 비교했다. 모두 차이 픽셀0, 브라우저 JS 오류0이었다. 회전·확대·초기화·화면 맞춤·자동 회전·윤곽선 제어, 모델 다운로드 크기, 외부 요청 없음, 모바일 넘침 없음도 확인했다. 이 검사는 뷰어 QA이며 게임 엔진 임포트나 플레이 성능 검증이 아니다.

`tools/`에 선별한 빌드 소스와 QA가 보관된다. 원래 머신의 `work/`와 node_modules 자체는 이식하지 않으므로 해당 폴더의 사용 설명과 잠금 파일로 의존성을 준비한다. 뷰어 수정 시 잔상 회귀 검사를 유지한다.

소스는 `tools/toon-viewer/viewer.js`, `tools/toon-viewer/viewer-template.html`에 있다. Node.js20 이상과 저장소 루트의 `package.json`/잠금 파일을 사용한다. 아래 명령은 저장소 루트에서 실행한다.

```sh
npm ci
npm run setup:browser
npm run build:viewer
npm run verify:viewer
npm run verify:ghosting
npm run verify:title
```

빌드는 `viewer.html`과 `viewer-v2.html`을 같은 수정본으로 갱신한다. Playwright Chromium을 우선 사용하며 필요한 브라우저 준비는 `setup:browser`가 맡는다. 시스템 브라우저/환경 변수 등의 대안과 추가 검사는 `tools/README.md`를 따른다. QA 결과는 `work/verification/`에 저장한다. `npm run capture:title`은 시작화면 PNG를 다시 캡처한다. Python/Pillow를 사용하는 자산 검사 도구가 있다면 해당 사용법으로 별도 의존성을 준비한다. 이 명령들은 시제품 재현·QA용이며 전투 게임 빌드가 아니다.

## 11. 추천하는 다음 개발 순서

현재는 사용자 요청으로 추가 개발을 멈추고 현재 작업의 Git 반영과 데스크톱 인계를 마친다. 아래 목록은 다음 개발 요청이 온 뒤 검토할 순서이며 자동 재개 지시가 아니다.

1. 저장소와 최신 기준 파일을 읽고 현재 상태를 짧게 보고한다. 엔진이 미정임을 확인하고 목표 플랫폼·팀 경험에 필요한 선택만 정리한다. 특정 엔진을 과거 확정 사항으로 주장하지 않는다.
2. 첫 전장과 별도6판 교전을 각각 실제 실행하고 입력·공격 예고·모델 가림과 전용 검사 기록을 확인한다. `67-playable-slice-priorities.txt`의 전체 완료 조건이나 최종 엔진 채택을 자동 충족했다고 보지 않는다.
3. 첫 전장에 구현한 단일 부모 연결 구조·부모 골조 절단·함포 단독 파괴를 기준으로 다음 범위를 정한다. 다른 에셋/엔진으로 옮길 때도 하위 묶음·남은 HP·파괴된 부품 표시와 중복 피해가 일관되는지 검증한다.
4. 첫 전장의 회수·소유권·화물 보존을 출발점으로 P2의 소켓 선택과 장착 편집 범위를 정한다. 회수는 자동 장착이 아니며 부품 복제를 막는다.
5. 첫 전장의 양력 위험·투하·귀환에 필요한 복구와 P4의 항구경제·정산·안전 경계 저장을 별도 설계·구현한다. 두 번 연속 출항해 부품·자원이 일관되는지 검사한다.
6. 기술 순환이 작동한 뒤 현재 선택 비행선의 모델을 부품별로 정리하고 엔진에서 손그림 표현을 맞춘다. 최종 아트를 계속 늘리기보다 하나의 표준 부품 세트를 검증한다.
7. P5에서 마라의 짧은 대사와 기억 포탑 하나를 넣는다. 전체4막과 모든 개인 임무를 동시에 구현하지 않는다.

8~12분 기술 시제품과30~40분 공개 데모 후보는 다른 범위다. 날짜·인원·비용은 아직 확정하지 않았으며 소요시간을 기획 문서의 플레이 시간으로 추정하지 않는다.

## 12. 저장소 운영과 재현

`outputs/`는 원본 기획과 사용자 확인용 산출물, `tools/`는 선별한 소스·빌드·검사 도구, `docs/`는 인수인계 문서다. `work/`, node_modules, 캐시, ZIP은 Git에서 제외한다. ZIP은 저장소 파일을 묶은 중복 배포물이므로 새 컴퓨터에는 Git/LFS 원본을 내려받으면 된다. 필요할 때 소스에서 다시 묶을 수 있다.

큰 바이너리는 `.gitattributes`의 LFS 추적 규칙을 따른다. 추가 자산을 저장할 때 규칙과 크기를 확인한다. 인증 토큰·API키·.env·계정 캐시를 출력하거나 커밋하지 않는다. 기존 생성 작업의 task ID와 비용 기록은 이력이며 새 생성 실행 지시가 아니다. 사용자가 새 생성/편집을 요청하지 않았다면 유료 Meshy나 새 무드보드를 자동 실행하지 않는다.

원본 이미지·기획 전문·검토 기록을 보존하고, 변경 파일·이유·실제 검증·남은 한계를 기록한다. 사용자 요청 없이 force push나 기록 삭제를 하지 않는다. 타 PC에서 문서 안의 옛 경로가 발견되면 원본 이력을 훼손하기보다 현재 도구와 새 참조에서 저장소 상대 경로를 사용한다.

### 아트 변형과 미구현 범위

청록 기계·황동·꿀빛 목재·크림 감개·산호 포인트를 공유한다. 초기 사각 보강판 제안은 실제 아트에서 원형 목재 받침으로 바뀌었다. 기획의 B=사각판 한 변은 원안의 상대 비율이며 원형 받침의 실제 미터·U·확정 소켓 치수로 환산하지 않는다. 박격포 받침·산호 밴드 위치, 포신/작살촉 색, 각진 받침과 포구, 작은 부품 단순화 등은 `art-review.txt`를 따른다. 한 장의 원화에서 추정한 후면과 틈까지 정밀 복제되었다고 주장하지 않는다.

현재 무기들은 독립 자산이지만 각 모델 내부는 단일 메시다. 가시적으로 나뉘어 보이는 포신·회전대·윈치·호스가 독립 오브젝트나 조준축·작동 리그로 완성된 것은 아니다. **부품 분리·장착 원점·피벗·발사 소켓·충돌·LOD·애니메이션·실제 사격과 전투 규칙은 후속 작업**이다. 손그림/셀 명암과 윤곽선은 작업대 런타임 재질이며 원본 GLB에 모든 엔진 공통 효과로 저장되지 않는다.

작업대의 '장착 배치'는 원본 비행선 옆에 외부 갑판 위치를 가정하여 색·방향·크기를 비교하는 시안이다. 기존 단일 메시 선체와 통합 포탑은 원본 그대로 보존했다. 이 배치는 기존 포탑 교체·실제 소켓 장착·부모 골조 연결·가림/포각/중량/전력·모듈 분리 기능을 구현한 것이 아니다. 방향/크기 조절과 카메라 자동 회전을 실제 포탑 조준·기계 동작으로 해석하지 않는다.

### 이어갈 때와 Git 상태

이번 무기 파일과 최신 문서는 **현재 로컬 작업 결과이며 이번 제작 요청에서는 git commit/push를 하지 않았다**. 이전 인수인계 시점에 원격 저장소 업로드를 완료한 사실은 그대로 보존한다. 그 과거 업로드에 이번6종이 이미 포함되었다고 가정하지 않는다. 다른PC에서 `git clone`/`git lfs pull`만 하면 아직 푸시하지 않은 이번 자산이 생기는 것은 아니다. 실제 원격 반영 여부는 최신 Git 상태와 원격 커밋으로 확인하고, push는 사용자 요청 범위에 따른다.

아트 자산 작업의 가장 가까운 추천은 **기관총 한 개와 선택 선체의 기존 포탑부터 기계 부품을 분리하고 장착 원점·yaw/pitch·포구 위치를 검증하는 것**이다. 새 사용자 요청이 우선이며, 전체 무기 리깅·업그레이드 추가·캐릭터 자동 리깅·새 Meshy 생성을 추정하여 시작하지 않는다. 전투 개발로 넘어갈 때는 여전히 엔진/플랫폼 결정과 P0~P4의 작은 항해 검증이 필요하다.

### 엔진 통합과 남은 한계

합성 시연의 포구는 원본 메시 끝점에서 추정한 근사 위치이며 정확한 표준 발사 소켓이 아니다. 기존 무기 원본을 보존한 별도 합성 파일이므로 **원본 포신 분리·조준축·장전/반동 리그·실제 소켓 장착을 완료한 것으로 해석하지 않는다**. 고정 연출의 도착 시간이 실제 충돌을 발생시키지 않는다.

실제 엔진이 충돌 위치·표면 법선·피해·가림·도탄·관통·상태를 판정해야 한다. 포구 +Z는 발사 방향, 피격면 +Y는 바깥 법선이다. 내장 이동은 진행 시연이므로 엔진 발사체 물리와 중복 이동하지 않는다. 상태가 종료되면 반복 표시를 중지하고, 풀 반환 때 animation time·표시용 root transform·부착 부모/끝점 참조를 리셋해야 한다. 이 규칙은 `recipes.json`의 통합 계약이며 실제 게임의 풀링 구현은 아니다.

무기 고유 명중과 공용 재질 피격은 하나를 주 효과로 고르고, 필요한 보조 조각만 추가해 큰 폭발·고리·연기 중복과 연결부 가림을 줄인다. 도형 크기와 시간은 아트 시제품 가설이며 새로운 피해·연료·회복·무적·상태 지속·소유권 규칙을 추가하지 않는다. 실제 collider·피해·physics·엔진 particle/shader·audio·성능 프로파일은 아직 없다.
